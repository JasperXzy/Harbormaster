# 任务列表与来源记录

2026-11-12，对应 F7.5、F14，以及前端 M2 的任务记录需求。先更新契约，再实现持久序号、来源记录和只读列表。

`GET /api/v1/jobs` 支持 `limit`（默认 50，1–200）、不透明 `cursor`、`account_id`、`instance_id`、`type`、`status`、`trigger`。结果按持久入队序号倒序；新增任务不会进入旧游标的后续页。未知账号或实例返回空列表，非法类型、状态、来源或游标返回 422。账号停用后仍可查历史。

Job 详情、列表和 SSE 使用同一数据对象，新增：

- `account_ids`：入队时确定的账号范围，空列表表示没有账号目标。
- `instance_id`：单实例目标；当前采集和 Telegram 测试任务为 null，不从内部 scope 字符串猜测实例。
- `trigger`：panel、cli、schedule、system、unknown；api 和 telegram 为相应消费入口预留，当前没有声称这些入口已实现。

HTTP 管理入口记录 panel，CLI 记录 cli，定时资源/CDT 扫描明确记录 schedule，即使调度由 run-once 调用。未特别标记的内部调用为 system。来源由可信入口设置，不接收客户端自报；重复请求复用已有活动任务时保留原任务来源。

迁移 `016_job_history.sql` 为既有记录按现有存储顺序建立稳定序号，来源默认 unknown，时间和结果原样保留。序号由 SQLite 自增表和插入触发器持久化，不依赖每次查询时重新编号；不对外暴露内部序号、scope、worker 租约或重试计数。备份快照包含此序号表。

列表与详情仅查询 SQLite，不依赖采集 engine 是否在工作，不发云请求、不创建新任务。现有单任务查询路径保持不变。开发模式提供两条合成记录、筛选、分页和对应详情。

## 前端对接答复

1. 任务列表已可对接。现有任务类型仍只有 refresh、permission_check、telegram_test，不能据此把电源操作视为已实现。前端需处理 cli/system/unknown 来源及 null 实例目标。
2. `PATCH /accounts/{id} {enabled:false}` 与 `DELETE /accounts/{id}` 使用同一停用逻辑：保留历史、停止采集、使旧采集任务失效并取消相关待发通知。DELETE 没有额外的数据清理；区别仅在成功响应分别为账号 JSON 和 204。当前前端只用 PATCH 可以。
3. 余额阈值已经按账号配置，见 [balance_low 契约说明](balance-alerts.md)，采用币种和十进制金额，不使用跨账号统一金额。
4. 当前账单接口仍没有经核实的应付净合计字段。逐行展示是与现有契约一致的行为；不能靠累加退款、调账等条目推导净额。若后续接入可靠的官方汇总来源，会先扩展契约。
5. 电源操作与期望状态尚未接通，当前不返回推测的 supports_stop_charging。手动电源逻辑可以先编写和模拟测试，不把 V3 未确认作为这部分代码开发的阻塞原因；真实资源写实验仍需单独授权。

没有修改 web/ 或 docs/design/，也未将前端自述页面完成当成后端已经完成整体验收。
