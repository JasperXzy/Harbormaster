# Harbormaster 分工

需求以 [PRD.md](PRD.md)（v0.5）为准。本文只规定谁做什么、双方在哪里对接。

## 当前执行方式（2026-11-11 更新）

用户已授权由 Codex 统一承担前端、后端、设计实现和联调；下文原 Claude / 后端分工保留为模块边界与后续交接参考，不再限制当前执行者修改 web/ 或 docs/design/。

- 前端独立为 web/（React + TypeScript），后端独立为 cmd/、internal/（Go）。各自有构建和测试，不互相导入源码。
- 面板唯一接口仍为 docs/api/openapi.yaml + SSE。凭据、数据库、云调用、计量、保护决策均属于后端。
- 默认独立运行：hm-server 纯 API，Vite / 静态服务器托管前端；生产通过同源反向代理对接。go:embed 仅保留为可选分发方式。
- 后续 Claude 可以替换 web/ 的设计和实现，遵守同一契约即可，无需重做后端。
- PRD 修改、真实云资源写操作、禁止 push / 合并 main 等原约束继续有效。本次职责调整不扩大云操作权限。
- 2026-11-12 用户授权：每个阶段完成并通过检查后先提交，再进行下一阶段，无需逐次询问。提交信息采用 `feat:`、`fix:`、`docs:` 等 Conventional Commits 格式，不添加 `M1 complete` 等里程碑前缀；涉及契约变更时在提交正文说明。

## 3. 接口契约

双方只通过 `docs/api/openapi.yaml` 对接，这是并行开发的前提。

**流程（每个里程碑一轮）**

1. 前端按该里程碑的页面，起草需要的接口（路径、字段、枚举）。
2. 后端评审：可行性、字段来源、性能；有异议直接改草稿并写明原因。后端对"能不能提供"有最终决定权，前端对"页面需要什么"有最终决定权；谈不拢交用户裁决。
3. 双方确认后冻结。前端用契约生成的模拟数据开发，后端按契约实现。
4. 冻结后要改，必须先改 `openapi.yaml` 并在文件顶部的变更记录里写一行，再改代码。

**通用约定**

| 项目 | 约定 |
|---|---|
| 前缀与格式 | `/api/v1/...`，JSON，UTF-8 |
| 时间 | UTC，RFC 3339 字符串；时区换算与显示由前端做 |
| 流量与金额 | 流量一律用整数字节；金额用字符串加币种字段；单位换算与格式化由前端做 |
| 枚举 | 英文 snake_case（如 `agent_status: not_installed / online / offline`）；中文显示由前端做 |
| 错误 | `{"error": {"code": "...", "message": "..."}}`，`code` 稳定可枚举，前端按 `code` 显示文案 |
| 认证 | Cookie 会话 + CSRF 请求头；未登录返回 401，无权限返回 403 |
| 异步操作 | 开关机、刷新等返回 `202` 与 `job_id`，前端查询任务状态（PRD F13.2） |
| 实时更新 | 实时估算、agent 状态、任务进度通过一条 SSE 事件流推送；其余页面按需轮询 |
| 分页 | 游标分页：`limit` + `cursor`，响应带 `next_cursor` |
| 数据新鲜度 | 凡是来自阿里云或 agent 的数据，响应里都带 `updated_at`，前端显示"截至 hh:mm" |

## 4. 前端与设计（Claude）

**职责**

- 把仓库外的静态 demo（`../demo/index.html`）改造成正式前端工程，保持其视觉风格。
- PRD F17 的全部页面：总览、实例、流量、自动化、费用、通知、设置、网络。
- 首次安装向导、登录页、Passkey 注册与登录的浏览器端流程。
- 所有状态的界面：加载中、空数据、出错、数据过期、agent 掉线、"未受实时保护"、试运行与模拟用量的醒目标记。
- 危险操作的确认交互（关机、释放实例要输入实例名等）。
- 图表：用量与预测、官方与实时估算对比、共享带宽入 / 出、延迟矩阵与曲线、线路逐跳。
- 桌面与手机两种宽度、深色与浅色。
- 界面文案；Telegram 通知与远程控制回复的文案模板（文字由前端定稿，发送逻辑由后端实现）。
- agent 安装引导的界面（安装命令的展示、复制、等待上线的反馈）。

**技术选择**

- Vite + TypeScript + React，不引入界面组件库，沿用 demo 的样式变量；图表沿用 demo 的自绘 SVG 方式。
- 构建产物输出到 `web/dist/`，由后端用 `go:embed` 打进 hm-server。
- 开发时 Vite 把 `/api` 代理到本机的 hm-server；后端未就绪时用契约生成的模拟数据。

**不负责**：任何 Go 代码、数据库、阿里云接口、agent、部署脚本。

## 5. 后端（GPT-6-Astra）

**职责**

- M0 技术验证：PRD 第 12 节 V1–V9，结论写入 `docs/m0/` 并提出 PRD 修订建议。
- hm-server：账号与资源发现、CDT 官方数据、计费对象识别、实时估算与对账、告警、通知发件箱、Telegram 机器人、自动化规则与期望状态、任务队列与租约、认证与会话、Passkey 服务端、API Key、加密存储、备份恢复、健康检查、子命令。
- hm-agent：注册绑定、公网流量计数、上报、掉线续报、测速与线路追踪、最小权限运行。
- 按契约实现 `/api/v1` 与 SSE 事件流；静态文件服务与单页应用回退（未知路径返回 `index.html`）。
- 部署：多平台构建、容器镜像、docker-compose、反向代理示例、agent 一行安装脚本。
- 后端测试，以及用模拟用量、试运行支持里程碑演练。

**需要为前端提供**

- 一个不依赖真实阿里云账号就能启动的开发模式（内置示例数据），方便前端联调。
- 没有 Node 环境时也能编译 hm-server（`web/dist/` 不存在时用占位页面）。

**不负责**：`web/` 下的任何文件、界面文案、视觉设计。

## 7. 协作规则

- 各自在独立分支开发（`fe/...`、`be/...`），由用户合并到 `main`。
- 提交说明里写明是否涉及契约变更。
- 发现对方的问题：写清复现步骤和期望结果交给用户转达，不直接改对方的代码。
- 需求有歧义时以 PRD 为准；PRD 没写的，提给用户决定，不自行假设后各做各的。
